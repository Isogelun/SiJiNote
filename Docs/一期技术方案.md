# 思迹笔记一期技术方案

| 项目 | 内容 |
| --- | --- |
| 文档状态 | 方案讨论稿，待技术评审与原型验证 |
| 产品范围 | 一期个人笔记；后续演进为团队知识协作产品 |
| 客户端目标平台 | Android、Windows、macOS |
| 核心质量目标 | 多平台行为一致、编辑流畅、本地草稿可靠、同步不丢数据 |

> 本文记录目标方案，不代表已实现或已通过兼容性、性能、部署验收。当前仓库仍是 Kotlin Multiplatform、Kuikly 与 Compose Desktop 原型。全面迁移 Flutter 应通过下文的验证门槛后再执行。

## 1. 目标与原则

思迹笔记一期聚焦个人知识记录与原文批注，长期方向是以文档和知识库为中心的团队协作办公产品。技术路线优先保证端上写作体验与数据可靠性，不因“高性能”目标提前拆分微服务或引入多种原生语言。

1. 多平台一致性指正文、批注、保存、冲突和恢复语义一致；桌面与移动端可以采用不同布局和输入方式。
2. Markdown 原文是笔记正文的唯一来源；预览树、索引、字数统计均可由原文重新生成。
3. 先保证本地持久化成功，再将内容同步到云端；网络成功与本地保存是两个不同状态。
4. Java 模块化单体作为后端起点；Rust 仅在性能分析或跨端算法复用证明确有收益后引入。
5. 所有性能数字均为验收目标，不代表当前测量结果或容量承诺。

## 2. 一期范围

| 优先级 | 功能 |
| --- | --- |
| P0 | 普通账号注册与登录、知识库与单层文件夹、笔记管理、Markdown 编辑与预览、个人高亮与批注、收藏、离线草稿、同步与冲突处理、30 天回收站 |
| P1 | 跨知识库搜索、Markdown 导入导出、只读快照分享；排期紧张时可先交付导出 |
| 后续 | 团队空间、成员与角色、共享知识库、评论与提及、通知、多人协同编辑、企业独立部署 |

一期不建设即时通信、审批、音视频或完整办公套件，不以未来团队协作需求为由提前引入微服务、消息队列或分布式缓存。

## 3. 总体架构

```text
Android / Windows / macOS
Flutter + Dart
SQLite 本地数据与待同步操作
        │ HTTPS / REST / JSON
        ▼
Java + Spring Boot 模块化单体
        │ JDBC
        ▼
PostgreSQL

可选：Rust 文档计算库，由客户端 FFI 或服务端模块按需调用
```

客户端和服务端通过版本化 API 契约解耦。Rust 是可选计算库，不是必需的独立微服务。

## 4. 客户端技术方案

| 模块 | 目标技术 | 约束与职责 |
| --- | --- | --- |
| 页面和交互 | Flutter + Dart | 共享业务状态与组件；桌面多栏、手机单栏等布局按平台适配 |
| Markdown 编辑 | Flutter 文本输入 + Dart | 一期整篇源码编辑与预览切换；中文输入法组词期间不改写编辑缓冲区 |
| Markdown 解析 | Dart 成熟解析库优先 | 生成预览和位置映射，不自研完整 Markdown 解析器；解析放入后台任务，避免阻塞输入 |
| 批注定位 | Dart 起步，必要时共享 Rust 实现 | 使用段落签名、偏移、引文快照及上下文重定位；无法唯一定位时标记失效，不静默跳到相似文本 |
| 本地持久化 | SQLite；可评估 Drift | 账号隔离保存笔记、草稿、批注、待同步操作和同步元数据；使用事务维护本地一致性 |
| 网络与同步 | Dart HTTP 客户端 + REST/JSON | 统一处理请求、重试、幂等、版本冲突和同步状态；UI 不直接承担同步协议 |
| 平台能力 | Flutter 插件，必要时平台通道 | 文件选择、安全存储、窗口生命周期和安装更新使用平台能力 |
| 原生计算 | Rust + Dart FFI（按需） | 只处理有明确输入输出的计算任务；按文档或文本块调用，不逐字符跨语言调用 |

### 4.1 编辑器与文本坐标

编辑状态必须保留 Flutter 文本输入、光标、选区和输入法组合状态。每次按键不得同步触发全篇解析、全量批注定位和网络请求。预览和格式化操作不能破坏中文输入法的组合输入。

若 Dart 与 Rust 共享偏移量算法，接口必须明确偏移单位和换行规范。测试覆盖中文、emoji、组合字符、CRLF/LF、重复引文及编辑后批注位置，避免 UTF-16 字符位置与 UTF-8 字节位置混用。

### 4.2 本地数据与草稿

本地数据库至少需要账号、知识库、目录、笔记、批注、待同步操作和版本元数据。已显示“已存本地”意味着相关 SQLite 事务已成功提交。网络不可用时保留待同步操作；应用重启后能够恢复草稿并继续同步。

## 5. 后端技术方案

| 层次 | 目标技术 | 职责 |
| --- | --- | --- |
| 语言与框架 | Java 21 LTS + Spring Boot 稳定版本 | 部署为一个应用，按业务边界组织模块 |
| API | HTTPS + REST/JSON + OpenAPI | 定义请求、响应、错误码、版本和幂等行为 |
| 认证授权 | Spring Security | 身份认证、可撤销会话、资源级权限检查 |
| 数据访问 | MyBatis + JDBC + HikariCP | 显式 SQL 与事务；按需求控制连接池 |
| 数据库 | PostgreSQL | 一期默认正式支持数据库 |
| Schema 管理 | 版本化迁移 SQL，迁移工具需验证兼容性 | 不依赖 ORM 自动建生产表 |
| 测试与观测 | JUnit 5、数据库集成测试、Actuator、结构化日志 | 验证业务不变量并监控延迟、错误和资源使用 |
| 文件存储 | 按需使用对象存储 | 文件内容与数据库业务元数据分离 |

建议后端模块边界：账号与会话、知识库与目录、笔记与版本、批注、同步与冲突、收藏、回收站、搜索、分享。模块在同一进程内协作，暂不按模块拆成网络服务。

密码使用成熟密码哈希实现；令牌和密钥不得写入日志。日志不记录笔记正文、密码或认证凭据。服务端需要按资源所属用户或团队空间验证授权，不能仅依赖客户端过滤。

## 6. 保存、同步与冲突

1. 客户端把草稿及待同步操作写入本地事务。事务成功后标记“已存本地”。
2. 停止输入约 800 ms 后发起自动同步；切换笔记、切后台和关闭窗口时优先完成本地落盘，不依赖网络请求作为唯一保存手段。
3. 上传操作带稳定操作 ID 和基础版本。服务端在事务中验证权限、检查版本并写入变更；重试同一操作不能重复创建数据。
4. 客户端收到与当前本地版本对应的服务端确认后才标记“已同步”。过期请求响应不能覆盖较新的本地状态。
5. 多端基于同一旧版本修改时，不静默覆盖。保留本地与云端内容，暂停该笔记自动覆盖并提示用户选择。
6. 删除状态也参与同步，避免离线设备重新上传时复活已删除内容。恢复级联删除内容时要保留“随级联删除”和“用户单独删除”的区别。

同步协议需要通过并发提交与断网重试测试验证，不假定单纯使用时间戳和 ID 排序就能保证变更不丢失。

## 7. 数据库兼容策略

一期只以 PostgreSQL 为正式验收目标。未来需要信创或更多主流数据库时，按客户要求明确数据库产品、版本、驱动、操作系统和 CPU 架构，再建立对应集成测试矩阵。

金仓、达梦、openGauss、MySQL、OceanBase 或 TiDB 均不能仅凭协议或内核相似就宣称已兼容。适配要覆盖迁移、数据类型、分页、唯一约束、锁、事务、大小写规则和错误行为。数据库迁移工具对具体国产数据库的支持要实测；必要时维护数据库专用迁移脚本。

为降低未来适配成本，业务逻辑不直接依赖数据库专有 SQL；主键由应用生成；复杂方言差异集中在 Mapper 或数据访问层。避免未经评估依赖 JSONB、ILIKE、ON CONFLICT、RETURNING 等 PostgreSQL 专有能力。

## 8. Rust 引入门槛

一期默认不引入 Rust。优先用真实数据分析 Flutter 与 Java 的端到端耗时，只有以下情况才考虑实现共享 Rust 库：

1. Markdown 解析或批注批量匹配被性能分析确认是明显热点，且跨语言调用和数据复制后的端到端体验仍有实测改善。
2. 客户端与服务端确实需要执行同一确定性算法，共享实现能够减少行为分歧，并且不违反正文加密边界。

优先候选是带源码位置映射的 Markdown 解析或批注锚点匹配。若瓶颈来自数据库 I/O、查询、锁竞争或网络，Rust 不会解决根因。不得以微基准提升代替用户可感知的端到端收益。

## 9. 加密、搜索与分享的产品决策

历史架构文档提出默认端到端加密；一期需求又包含服务端正文搜索和免登录分享。实现正文存储、搜索和分享之前，必须明确服务端是否可读取正文。

| 决策 | 影响 |
| --- | --- |
| 端到端加密 | 服务端保存密文，不能直接进行常规明文全文搜索；分享需要显式发布或密钥共享设计；还需定义密钥备份与多设备恢复 |
| 服务端可读取正文 | 搜索和快照分享较直接；需要落实传输与存储保护、访问控制、备份保护和日志脱敏，不得宣称服务端无法解密 |

个人批注默认仅本人可见，不包含在分享正文中。分享链接需要不可猜测、可撤销，笔记删除后失效。

## 10. 更新与部署

### 10.1 客户端更新

生产环境不把 Flutter 开发期 Hot Reload 当作代码热更新方案。一期目标是可靠安装更新，而非运行中替换 Dart 代码：

- Android 按实际分发渠道和平台政策更新。
- Windows/macOS 商店版本走商店更新；独立分发版本使用签名安装包更新。
- 更新包下载后验证签名；用户草稿已落盘后再安装或在下次启动生效。
- Dart 业务代码、Flutter 引擎和 Rust 库随应用包发布。在线文案或配置不得下发可执行逻辑。
- 更新验收覆盖下载中断、签名失败、升级后草稿可读和 SQLite 迁移失败恢复。

### 10.2 服务端部署

初期按现有 2 核 2 GB Alibaba Linux 服务器验证：HTTPS 反向代理、Java 应用和 PostgreSQL。限制 JVM 内存与数据库连接数；监控整机内存、CPU、磁盘空间、I/O 和数据库等待。备份保存到异机或对象存储并实际演练恢复。

同机部署是待压测的初期方案，不承诺固定用户容量；不要仅凭服务器规格断言某数据库一定可用或不可用。构建和集成测试放在开发机或 CI。初期不引入 Redis、Elasticsearch、消息队列、Kubernetes 或微服务，除非监测数据或产品需求证明必要。

## 11. 性能与一致性验收

以下是目标值，必须在发布构建和明确记录的设备、数据规模、网络条件下测量，不是已实现指标。

| 场景 | 验收目标 |
| --- | --- |
| 冷启动首屏 | 目标不高于 1 秒；区分冷启动与热启动，记录测试设备 |
| 中文编辑 | 一万字 Markdown 文档输入到显示目标不高于 50 ms；验证 Android、Windows、macOS |
| 目录树 | 1,000 个节点渲染目标不高于 500 ms |
| 搜索 | 若一期交付，约定数据规模下 P95 目标不高于 500 ms；超过 5 秒提示超时 |
| 本地恢复 | 已标记“已存本地”的草稿在断网、强制结束和重启后可恢复 |
| 批注一致性 | 编辑正文后能稳定重定位；歧义或失败时标记失效，不跳至错误文本 |
| 多端同步 | 弱网重复请求不产生重复数据；并发修改不静默覆盖；恢复网络后状态可解释 |
| 服务端负载 | 在 2C2G 上记录保存与同步的 P50/P95、错误率、CPU、峰值内存、数据库连接与等待；据实决定是否扩容或拆分 |
| 更新安全 | 更新包签名校验通过才安装；升级后本地草稿和数据库可用 |

## 12. 实施阶段

1. **Flutter 编辑器原型**：三端验证中文输入、长文编辑、撤销重做、预览切换和批注重定位；用同一测试文档对照当前原型。
2. **本地数据闭环**：SQLite 草稿、批注、目录与待同步操作；覆盖断网、进程中断和数据库迁移。
3. **后端最小闭环**：Java 登录、笔记版本、幂等保存、权限检查和同步确认；完成双设备并发与重试测试。
4. **P0 功能**：知识库与目录、收藏、回收站、完整编辑状态和冲突交互。
5. **P1 功能**：按加密决策和排期交付搜索、导入导出、分享；逐项建立验收测试。
6. **团队协作演进**：先做团队空间、成员角色、共享知识库与评论；多人同时编辑需求成立后再评估实时协同协议。

全面迁移前的门槛是 Flutter 三端原型通过编辑一致性、草稿恢复和性能验收。若未通过，应先修正输入、解析、存储或平台适配问题，不以“换原生语言”作为默认补救。
